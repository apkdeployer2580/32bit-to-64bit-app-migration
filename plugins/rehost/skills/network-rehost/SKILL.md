# 죽은 서버 되살리기

원본 서버는 없어졌지만 **게스트의 네트워크 코드는 멀쩡하다.** 목표는 게스트
바이너리를 한 바이트도 고치지 않고 우리 서버와 대화시키는 것이고, 그래서
리다이렉트는 **호스트 한 곳**에만 있다.

```rust
/// The guest's hardcoded endpoints, from the binary's own strings. There is
/// usually more than one: auth, game, and a separate billing/backup host.
const DEAD_HOSTS: [&str; 2] = ["<auth host from .rodata>", "<billing host>"];

fn redirect_target(host: &str, port: u16) -> (String, u16) {
    if DEAD_HOSTS.contains(&host) { (OUR_HOST.into(), OUR_PORT) }
    else { (host.into(), port) }
}
```

주소는 `strings` 로 찾는다. **포트도 같이 확인하라** — 같은 호스트를 여러 포트로
쓰는 경우가 흔하고(메인 / 결제 / 백업), 그중 일부만 구현하게 된다.

## 1. 소켓이 아예 안 열릴 때 — 호스트 쪽 두 가지를 먼저 의심하라

실제로 막았던 것 둘, **둘 다 우리 쪽 버그**였다.

### (a) "네트워크 사용 가능?" 질의에 0을 답하고 있었다

게스트의 연결 함수가 소켓을 만들기 **전에** 플랫폼에 네트워크 상태를 묻고,
유효값이 아니면 **-1로 즉시 반환**하는 구조가 흔하다. -1은 실패 콜백조차 부르지
않으므로(특정 코드만 콜백을 부른다) **아무 일도 안 일어난다** — 로그에 `connect`
시도 자체가 없다. 게임 자체 타임아웃만 돌다가 "문제가 발생했습니다"가 뜬다.

유효값이 무엇인지는 디스어셈으로 확정하라. `(ret - 1) > 1` 같은 부호 없는 비교면
유효값은 `{1, 2}` 뿐이다.

### (b) 권한이 없었다

"서버가 죽었으니 아무 권한도 요청하지 않는다"는 전제로 매니페스트에서 INTERNET 을
빼 두면, 사설 서버를 세우는 순간 그 전제가 무효가 된다. `connect` 가 프로세스를
떠나기 전에 EPERM 으로 죽는다.

**교훈**: 로그에 `connect` 시도 자체가 없으면 게스트가 시도 전에 포기한 것이고,
시도는 있는데 EPERM 이면 플랫폼 권한이다. 이 두 줄을 구분해서 찍어라.

## 2. 프로토콜 해독 — 실캡처가 정답지다

게스트가 보내는 것을 있는 그대로 찍는 것부터 시작한다. 전형적인 요청 프레임:

```
[u32 BE 전체길이(자기 포함)]
  +0   32B  tag    "AH_1.0.0"
  +32  16B  model  "SM-G991N"
  +48  12B  os     "ANDROID"
  +60  44B  ver    "2.X"
  +104 ..   body = [u8 len(자기 포함)][u32 BE opcode][payload]
```

길이 필드가 정확히 맞아떨어지는지로 프레이밍 가설을 검산하라(130B 프레임의 길이
필드가 130, body 가 0x16 = 22B 이면 맞다). 빅엔디안인 것은 게스트가
`putShort/putInt` 류 헬퍼로 채우기 때문인 경우가 많다.

## 3. **응답 프레임은 요청과 형식이 다르다** — 여기서 가장 오래 막힌다

응답을 보내도 수신 이벤트가 안 오면, **게스트가 몇 바이트를 요청하고 몇 바이트를
받았는지**를 찍어라. 이 한 가지가 문제를 즉시 드러낸다:

```
recv want=1    got=1: 00              ← 선두 1바이트를 먼저 읽는다
recv want=4    got=4: 00 00 0c 00     ← 이걸 길이로 해석 = 3072
recv want=3068                        ← 영원히 기다린다
```

응답이 **정확히 1바이트 어긋나** 있었다. 실제 형식:

```
[u8 선두][u32 BE len][body]        body 는 정확히 len-4 바이트
```

1바이트를 붙이자 그대로 통했다.

### 채널마다 프레이밍이 다르다

한 게임 안에서 **세 가지 프레이밍**이 공존한 실제 사례:

| 채널 | 응답 형식 |
|---|---|
| 메인 게임 서버 | `[u8 선두][u32 BE len][body]` |
| 결제/스마트요청 소켓 | `[u32 BE len][body]` — **선두 바이트 없음** |
| 데이터 백업 서비스 | 바깥 길이 접두가 **아예 없음**. `[u8 cmd][u8 status][u8 n][n바이트][cmd별 추가]` |

하나를 풀었다고 다른 채널에 그대로 쓰면 안 된다. **채널마다 수신 콜백 함수를
따로 읽어라** — 그 함수가 총 길이를 어떻게 계산하는지가 곧 형식이다.

### 소켓 계층이 벗겨내는 헤더를 계산에 넣어라

소켓 계층이 길이 4바이트를 벗겨내고 body 만 상위로 올리면, 디스패처가 보는
카테고리/서브 오프셋은 **body 기준**이다. 이걸 놓치면 항상 4바이트 밀린다.

## 4. `CS_NET_DEBUG` 류 스위치를 처음부터 만들어라

찍어야 할 것:

* `connect(host, port)` 시도와 리다이렉트 결과 (**원래 주소도 같이**)
* `recv want=N got=M: <앞 16바이트 hex>`
* `send N bytes: <앞 16바이트 hex>`
* 게스트 콜백 진입 (`netLibCB(event, len, ptr)`)과 디스패치된 핸들러 이름

이 네 줄이면 프로토콜 버그의 90%가 한 번에 보인다.

## 5. 클라이언트 상태를 밖에서 읽어라

프로토콜 핸들러가 특정 상태에서만 동작하는 경우가 많다(예: sub=2 핸들러가
상태 0xa~0xd 에서만). 그 상태 바이트의 게스트 주소를 찾아 프로브의 `--peek` 로
읽으면 "서버 응답은 맞는데 클라가 안 받는다"를 즉시 구분할 수 있다.

## 6. 파괴적인 기능은 **양방향이 다 되기 전에는 열지 마라**

세이브 백업/복원 같은 기능은 업로드 성공의 마지막 단계가 **로컬 세이브 삭제**인
경우가 있다. 업로드만 구현하고 다운로드를 안 만들면, 실기기에서 그 메뉴를 쓰는
순간 세이브가 사라진다.

착수 전에 각 커맨드가 **무엇을 지우는지** 먼저 표로 정리하라. 그리고 구현이
끝날 때까지 그 엔드포인트는 아예 응답하지 않는 편이 안전하다(게스트가 자체
타임아웃으로 안전하게 실패한다).

세이브가 안전한지 확인하는 방법은 간단하다 — **기능 실행 전후로 세이브 파일의
해시를 비교**하라.

## 7. 서버 쪽

* 별도 디렉터리(`server/`)에 두고 **README 에 프로토콜 전문**을 남겨라. 그것이
  이 프로젝트에서 가장 잃어버리기 쉬운 지식이다.
* 응답 상태 바이트 같은 것은 **핫 조정 가능한 설정 파일**(`replies.json`)로
  빼라. 실기기 검증 중에 서버를 재시작하지 않고 값을 바꿀 수 있다.
* 헤드리스 셀프테스트를 붙여라 — 로직 + 실제 asyncio 소켓 왕복.
* **포트를 연 지 몇 분 만에 스캐너가 붙는다.** TLS 를 붙일 수 있으면 붙이고,
  게스트 쪽에 지원이 없어 평문이라면 그 사실을 문서에 명시하라.

## 8. 도달 불가능한 코드에 속지 마라

프로토콜을 완벽히 해독하고 서버까지 구현했는데 **그 경로가 이 빌드에서는 절대
실행되지 않는** 경우가 있다. 실제 사례: 결제 요청 함수가 특정 전역 == 3 일 때만
불리는데, `.text` 전체의 리터럴을 훑어 그 전역에 저장되는 값을 전부 뽑으면
`0/1/2/5/0xa/0x32` 뿐 — **3이 없다.**

진짜 경로는 소켓이 아니라 **JNI 플랫폼 호출**이었다(→ `guest-behavior-patching`
의 "죽은 플랫폼 서비스에 답하기").

**착수 전에 확인하라**: 그 경로를 여는 조건이 실제로 성립하는가. 확인 방법은
그 전역/플래그에 **저장하는 모든 지점**을 전수 조사하는 것이다.
