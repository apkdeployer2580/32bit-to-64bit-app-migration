# 프레임 최적화 — 게스트 함수를 호스트로, 픽셀 단위로 같게

해석 실행은 네이티브의 수십분의 일이다. 그래도 게임이 도는 이유는 **비용이
균등하지 않기 때문**이다. 실측에서 게스트 명령어의 **3분의 2가 함수 하나**에
있었다. 그 함수 하나를 호스트로 옮기면 그 3분의 2가 사라진다.

이 스킬은 그 작업의 **순서와 증명 방법**이다. 개별 픽셀 루프를 어떻게 옮기는지는
`references/` 에 있다.

## 0. 절대 규칙 두 개

**규칙 1 — 호스트 경로는 원본을 비트 단위로 재현하거나, 아니면 거절한다.**
"거의 같다"는 없다. 블렌드 반올림 방향 하나, 클립 1픽셀, 팔레트 니블 순서 —
전부 화면상으로는 멀쩡해 보이고 전부 틀렸다. 그리고 그 틀림은 당신이 재생하지
않은 어떤 장면에서 깨진 스프라이트 하나로 나중에 나타난다.

호스트가 감당 못 하는 입력(커스텀 함수 포인터 연산자, 예상 밖 픽셀 포맷,
매핑 안 된 테이블)이면 **아무것도 건드리지 않고 `false` 를 돌려주고 해석기가
출시된 코드를 그대로 돌리게 한다**. 거절은 실패가 아니라 설계다.

**규칙 2 — 증거는 "픽셀 단위 동일"이다.**
`NO_PATCH=1` 로 한 번, 패치 켜고 한 번, **같은 결정적 재생**을 돌려서 덤프
프레임이 전부 같아야 한다. 이것 없이 커밋하지 않는다.

```bash
NO_PATCH=1 probe ... --out out_ref  --storage out_ref/st
         probe ... --out out_test --storage out_test/st
python ${CLAUDE_PLUGIN_ROOT}/scripts/ab_compare.py out_ref out_test
```

## 1. 평균이 아니라 분포를 봐라

"보스전 끝나고 렉이 걸린다", "몬스터가 많으면 느려진다" — 이 두 신고는
**평균에 전혀 나타나지 않는다.**

실제 측정 예:

| | 평균 | p90 | p99 | 최악 | 33 ms 초과 |
|---|---|---|---|---|---|
| 이식 전 | 10.6 ms | 20.0 | **84.6** | 310.7 | 205/2600 (7.9%) |
| 블리터 이식 후 | 0.7 ms | 1.4 | **2.2** | 202.1 | 1/2600 |
| 암호화까지 | 0.6 ms | 1.4 | 2.2 | **47.6** | 2/2600 |

평균 10.6 ms 는 94 fps 다. **처음부터 문제가 아니었다.** 문제는 꼬리였고,
꼬리를 만든 것은 프레임당 몇 번 안 도는 무거운 함수들이었다.

그래서 매 실행 끝에 이것을 찍는다:

```bash
python ${CLAUDE_PLUGIN_ROOT}/scripts/frame_stats.py after.txt --before before.txt \
    --inst-per-sec <기기 실측> --budget-ms 33
```

**가장 비싼 프레임 번호**를 같이 찍어라. 그 번호가 다음 명령이다:
`--dump <그 프레임>`, 그리고 그 프레임만 프로파일.

## 2. 무엇을 이식할지 고르기

```bash
probe ... --profile
```

게스트 PC 샘플을 **심볼 이름으로 접어서** 상위 20개를 낸다. 심볼이 살아 있다면
이 목록이 곧 작업 목록이다.

읽는 법:

* **한 함수가 50%를 넘으면** 다른 건 보지 마라. 그것만 옮긴다.
* **프로파일이 평평해지면**(1위가 10% 미만) 그리기 최적화는 끝난 것이다.
  남은 스파이크는 렌더링이 아니다 — 세이브 암호화, 에셋 로드, 아카이브 스캔 같은
  **드물지만 한 프레임을 통째로 먹는 것들**이고, 그건 분포의 꼬리에서 찾는다.
* **전체 프로파일과 한 프레임 프로파일은 다른 질문에 답한다.** 스터터를 찾을
  때는 반드시 그 프레임만 프로파일하라. 전체 평균은 그것을 평탄화해서 없애 버린다.

### 거의 항상 나오는 후보들 (우선순위 순)

| 후보 | 왜 느린가 | 배수 |
|---|---|---|
| **프레임버퍼 블리터** (스프라이트/타일 그리기) | 픽셀마다 클립 검사 10여 번 + 행 주소 재계산. 16비트 하나 옮기는 데 100명령 | 가장 크다. 첫 번째로 |
| **회전/배율 블리터** | 위와 같고 누산기까지 | 두 번째 |
| **폰트 스택** | 픽셀마다 함수 3개 호출, 카운터·커서가 전부 GOT 간접 전역 | 타이틀 화면의 88% 사례 |
| **알파 채움 / 사각형 채움** | 같은 구조 | 대화창 프레임의 34% 사례 |
| **박스 블러 (간유리 배경)** | O(w·h·k²) + 픽셀마다 나눗셈 3번 | **한 프레임에 1.2초** 사례 |
| **`__divsi3` / `__udivsi3`** | ARMv5TE 에 나눗셈 명령이 없다. 모든 `/` 가 55명령 루프 호출 | 전역적으로 효과 |
| **DES/암호화** (세이브·데이터 로드) | 비트 배열(1비트를 1바이트에) 위에서 도는 구현. **바이트당 3,500 명령** | 오토세이브 0.7초 정지 |
| **아카이브 조회** | 조회할 때마다 전체를 4바이트씩 재스캔 | 부팅~메뉴에 `fread` 87만 회 사례 |
| **memcpy/memset/strlen** | import 라면 이미 HLE 다. 게스트 내부 구현이면 이식 대상 | |

## 3. 어디에 후크를 거는가

**심볼 이름으로 건다. 주소로 걸지 않는다.** 다르게 빌드된 게스트에서는 조용히
틀리는 대신 그냥 설치가 안 되게.

```rust
pub const PATCHED: [(&str, Patch); N] = [
    ("internalGrpCopyFrameBuffer", Patch::Blit),
    ("__divsi3",  Patch::Div { signed: true }),
    ...
];
```

### 함수 진입점에 `bl` 이 하나도 없을 수 있다

픽셀 포맷·상태·vtable 로 고른 **함수 포인터**로만 진입하는 함수가 있다.
`bl` 만 찾으면 죽은 코드로 보이고, 실제로는 프레임의 99%를 태우고 있다.

```bash
python ${CLAUDE_PLUGIN_ROOT}/scripts/xref.py libgame.so TheFunc --words
```

`--words` 는 그 주소를 **32비트 워드로 담고 있는 곳**(리터럴 풀, GOT, 점프
테이블, vtable)을 찾는다. 직접 호출 0 + GOT 에 주소 있음 = 함수 포인터 진입이다.
그 경우 진입점 후크는 **모든 호출자에 대해** 맞아야 하므로, 호출자를 전부 읽고
각각의 인자 규약을 확인해야 한다.

### 래퍼가 아니라 **공용 드라이버**를 후킹하라

방향(암호화/복호화)이나 모드에 따라 상태를 만드는 얇은 래퍼들이 있고, 그 아래
공용 본체가 있다면 **본체를 후킹한다.** 래퍼가 이미 세운 상태를 그대로 물려받게
되므로 그 상태를 모델링할 필요가 아예 없어진다. 래퍼를 후킹하면 그 변형까지
전부 재현해야 한다.

## 4. 스위치와 카운터 — 없으면 증명도 진단도 못 한다

```
NO_PATCH=1     호스트 구현 전부 끔 (최종 A/B)
NO_FNT=1       폰트만 끔          (개별 기여 측정)
NO_SCREEN=1    스크린 블리터만 끔
NO_ROT=1       회전 블리터만 끔
NO_DES=1       암호화만 끔
```

개별 스위치가 중요한 이유: `NO_PATCH=1` 전체 A/B 는 **매우 느리다**(무패치
인터프리터는 150억 명령). 나머지를 켠 채 하나만 끄면 A/B 가 쓸 만한 속도로 돈다.

그리고 **패치마다 서브 횟수와 거절 횟수를 센다**:

```
host patches: 35162 screen, 1204 rot, 88 fnt, 3 des, 2 declined to the guest
```

* **0이면 설치조차 안 된 것이다.** "이식했는데 왜 안 빨라지지"의 90%가 이것.
* 거절이 많으면 그 입력 조합을 마저 구현할 가치가 있다는 뜻이다.
* 디버그 스위치로 **거절된 인자 조합을 찍게** 해 두면 무엇을 마저 구현할지가
  바로 나온다 (`SCREEN_DEBUG=1` 이 회전 코드/포맷/alpha/level 분포를 찍는 식).

## 5. 디스패치 비용을 조심하라

패치 주소를 매 게스트 명령마다 **선형 스캔하면 안 된다.** 패치 주소 창
(`lo..hi`)이 `.text` 의 대부분을 덮게 되므로 거의 모든 명령이 그 값을 낸다.

```rust
if pc >= self.patch_lo && pc <= self.patch_hi {          // 예측 잘 되는 비교 2회
    if let Ok(i) = self.patches.binary_search_by_key(&pc, |(a, _)| *a) { ... }
}
```

정렬 + 이진 탐색. 패치를 추가할수록 나빠지는 구조로 두지 마라.

## 6. 순서 — 실제로 이 순서가 맞았다

1. **가장 큰 블리터 하나.** (전체의 2/3 이던 것)
2. **나눗셈 헬퍼.** 싸고 전역적이다.
3. **회전/배율 블리터**, 처음에는 쉬운 경로만. 거절 카운터로 남은 경로를 본다.
4. **폰트 스택 전체.** (개별 픽셀 함수만 옮기면 호출 오버헤드가 남는다 —
   `DrawString` 본체까지 옮겨야 한다.)
5. **알파 채움 / 블러** — 여기서 "메뉴 열 때 1.2초 멈춤"이 사라진다.
6. 프로파일이 평평해진다. **이제 분포의 꼬리를 본다.**
7. **암호화·에셋 로드** — 남은 33ms 초과 프레임들.
8. 거절하던 경로들(전치 회전 코드 등)을 마저.

각 단계 뒤에 **반드시** A/B 픽셀 비교 + 프레임 분포 비교.

## 7. 렌더링이 아닌 스파이크

프로파일이 평평해진 뒤 남는 것들. 전부 "가끔, 그러나 한 프레임을 통째로".

* **오토세이브** — 세이브 크기가 바이너리에 박혀 있는 경우가 많다. 암호화
  바이트당 명령 수 × 그 크기 = 정지 시간. 이것이 "보스전 끝나고"의 정체.
* **캐시 없는 데이터 로드** — 몬스터가 생길 때마다 파일을 읽고 복호화하는 식.
  이것이 "몬스터가 많을 때"의 정체. 원인이 같은 함수라는 것을 알면 한 번에 잡힌다.
* **오디오 디코드를 프레임 스레드에서 하는 것.** 한 프레임에 55~140 ms, 그것도
  오디오 콜백이 원하는 뮤텍스를 쥔 채로. **워커 스레드로 빼라.** 원본도 대개
  비동기였다(플랫폼 미디어 플레이어). 프로브만 동기로 두어 재현성을 지킨다.
* **같은 리소스 재디코드.** 캐시 맵을 기록만 하고 조회하지 않는 버그가 흔하다.

## 8. 기기에서 프레임 시간을 쪼개서 보라

```
perf: guest 12.4ms  copy 0.8ms  present 1.9ms   (46 M inst/s)
```

`guest` / `copy`(프레임버퍼→서피스) / `present` 를 나눠 찍어야 "해석기가 느리다"와
"presenting 이 느리다"를 구분할 수 있다. 대개 present 는 1~3 ms 로 처음부터
문제가 아니고, 남은 건 전부 게스트 실행 시간이다 — 그러면 이 스킬로 돌아온다.

그리고 **기기의 `M inst/s` 를 한 번 실측해서 상수로 박아 두라.** 명령 수를
사람이 느끼는 ms 로 바꾸는 데 필요하고, 명령 수 자체는 기기 무관하게 정확하다.
