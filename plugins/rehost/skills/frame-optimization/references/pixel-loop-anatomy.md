# 픽셀 루프의 해부 — 옮길 때 실제로 만나는 구조

피처폰/초기 모바일 게임의 렌더러는 서로 놀랄 만큼 닮았다. 아래는 **이식할 때
반복해서 만나는 구조와, 각각에서 틀리기 쉬운 지점**이다.

## 1. 왜 그렇게 느린가 — 구조적인 이유들

* **픽셀마다 클립 비교 10~12번 + 행 주소 재계산.** 16비트 하나 옮기는 데 게스트
  명령 100개. 루프 밖으로 들어내는 것이 호스트 구현이 공짜로 얻는 것 전부다.
* **켜진 픽셀마다 함수 호출 2~3개** (폰트 스택의 전형).
* **카운터·커서·누산기가 전부 GOT 간접 전역.** 픽셀 하나에 리터럴 로드 + GOT
  로드 + 포인터 로드가 반복된다.
* **나눗셈 명령이 없다.** ARMv5TE 는 `/` 를 55명령짜리 시프트 루프 호출로 만든다.
  픽셀당 나눗셈 3번짜리 루프가 실재한다.
* **O(w·h·k²)** 를 그대로 쓴 블러.

## 2. 회전 코드 아홉 개가 아핀 식 하나로 접힌다

회전·미러 블리터는 보통 코드 0..8 의 **열여덟 개 블록**으로 펼쳐져 있지만, 전부
소스를 `j = 0..h`, `i = 0..w` 로 **같게** 걷는다. 차이는 **어디에 쓰는지**뿐이다:

```
D(i, j) = d0 + j·DR + i·DI
```

| code | d0 | DR | DI | |
|---|---|---|---|---|
| 0 | `dstW·dy + dx` | `+dstW` | `+1` | 항등 |
| 1 | `dstW·dy + dx+w-1` | `+dstW` | `-1` | 좌우 미러 |
| 2 | `dstW·(dy+h-1) + dx` | `-dstW` | `+1` | 상하 미러 |
| 3 | `dstW·(dy+h-1) + dx+w-1` | `-dstW` | `-1` | 180° |
| 4 | `dstW·dy + dx+h-1` | `-1` | `+dstW` | 90° CW |
| 6 | `dstW·(dy+w-1) + dx` | `+1` | `-dstW` | 90° CCW |
| 7 | `dstW·(dy+w-1) + dx+h-1` | `-1` | `-dstW` | 전치+양미러 |
| 8 | `dstW·dy + dx` | `+1` | `+dstW` | 순수 전치 |

`D` 가 아핀이므로 극값이 네 꼭짓점에 있다. 그래서 **전치 코드까지도 목적지가
연속 구간 하나**다 — 블록으로 읽어 고치고 한 번에 되쓸 수 있다.

### 전치(4/6/7/8)에서 틀리기 쉬운 곳

* 목적지 사각형이 **`sh` 폭 × `sw` 높이**로 뒤집힌다. 즉 `scaleX` 가 회전된
  스프라이트의 **세로** 크기를 정한다.
* 그런데 **`xstep`/`ystep` 은 같이 뒤집히지 않는다.** 여전히 소스 자기 폭·높이의
  스텝이다. 화면 축마다 **반대쪽** 소스 축이 붙는 것뿐이다.
* 그래서 **행마다 `row_off` 를 미리 계산하면 안 된다.** 행 우선 코드에서 하던
  대로 호이스팅하면 **각 행의 첫 픽셀만 맞고 나머지가 전부 틀린다.**
* 클립은 화면 축에 붙으므로 검사는 그대로고 **범위만 교환**된다.
* `hflip = {1,3,6,7}`, `vflip = {2,3,4,7}`.

### 같은 번호가 두 함수에서 다른 뜻일 수 있다

한 함수에서 코드 5가 "행 우선 180°"인데 형제 함수에는 `mov r4,#5` 가 **아예 없고**
같은 180°를 3으로 번호붙이는 일이 있다. **두 함수의 코드 표를 공유하지 마라.**
확인은 기계적으로: 코드 레지스터에 대입하는 지점을 전수 조사한다.

## 3. 팔레트 소스 픽셀

```c
head = (img[0x14] + 4) * 2 + 1;          // 헤더 건너뛰기 (게임마다 다름)
fmt  = *(u8*)img[0x20];                  // 예: 0xb = 4bpp, 0xc = 8bpp, 그 외 반환
4bpp: stride = (img[0] + (img[0] & 1)) >> 1;  base = head + (sx >> 1) + stride*sy;
8bpp: stride =  img[0];                       base = head +  sx       + stride*sy;

8bpp: idx = pix[base + j*stride + i];
4bpp: k = i + (sx & 1);
      b = pix[base + j*stride + (k >> 1)];
      idx = (k & 1) ? (b & 0xf) : (b >> 4);   // 짝수 절대열 = 상위 니블
s = pal16[idx];
```

주의:

* 게스트는 이걸 "홀수 헤드 → 두 픽셀씩 짝 루프 → 홀수 테일 → 행 전진" 네 조각으로
  펼쳐 쓴다. 위 식과 동치임을 **짝/홀 `sx` 양쪽에서, 음수 `sx` 에서도** 확인하라
  (`sx>>1` 은 산술 시프트, `sx&1` 은 생 AND).
* **투명색 비교가 32비트일 수 있다.** 팔레트는 u16 인데 전역 투명색이 u32 워드면,
  상위 비트가 있을 때 **아무것도 투명하지 않다.** u16 으로 자르면 틀린다.
* 포맷 검사 **전에** 일어나는 부수효과(`img[0x1c] = img[0x10]` 같은)를 놓치지 마라.
  거절할 때도 그 부수효과는 일어나야 할 수 있다 — 그렇다면 거절 자체가 불가능하니
  구조를 다시 봐야 한다.

## 4. 블렌드 파이프라인 두 종류

### (a) 산술 블렌드 (단순 알파)

```c
r = (src_r*a + dst_r*(255-a)) >> 8;   // 채널별, 565 마스크 유지
```

### (b) 레벨 룩업 테이블 — **산술로 대체하면 안 된다**

```c
out_ch = table[(level*32 + src_ch)*32 + dst_ch]     // ch = 5비트
```

* 녹색도 **5비트로 뽑아 조회하고 결과를 2배**해 6비트로 되돌린다.
* `level == 0x10` 은 별도 모드일 수 있다(예: 그레이스케일
  `gray = (6r + 4g + 2b) >> 4`, 녹색은 `gray*2`).
* 그 **다음에** `alpha <= 0xfe` 면 결과를 dst 와 한 번 더 가중 혼합한다:

```c
a5 = (alpha & 0xf8) >> 3;  a6p1 = ((alpha & 0xf8) >> 2) + 1;  a5p1 = a5 + 1;
r  = (r  * a5p1 + dr  * (32 - a5p1)) >> 5;
g6 = (g6 * a6p1 + dg6 * (64 - a6p1)) >> 6;
b  = (b  * a5   + db  * (32 - a5))   >> 5;   // 파랑만 +1 없는 가중치 — 출하된 비대칭
out = (r << 11) | ((g6 << 5) & 0x7e0) | (b & 0x1f);   // 빨강은 마스크 없음
```

마지막 줄의 "빨강은 마스크 없음"은 실수가 아니다 — 5비트 평균은 비트 16으로
넘칠 수 없다.

## 5. 폰트 스택

* 폰트 객체의 필드(셀 폭/높이, ASCII 전진폭, 자간, 공백폭, y 오프셋, 알파,
  모드, 성분당 바이트, 글리프 스트라이드, 본체/외곽 색)를 먼저 표로 정리하라.
* 모드가 "외곽 2패스"면 **같은 문자열을 두 번** 그린다.
* 조합형 문자(한글 등)는 **초/중/종성 비트맵을 스크래치 버퍼에 OR 합성**한 뒤
  렌더한다. 그 버퍼 크기(예: 32바이트)를 넘는 스트라이드면 거절해야 한다.
* 완성형↔조합형 변환의 **에러 경로까지** 재현하라. 범위 밖 입력에 대해 원본이
  로그를 찍고 `?` 를 그린다면 그것이 정답이다(원본에도 있던 잡음).
* **블렌드 LUT 가 자기 크기를 넘어 읽힐 수 있다.** 누산기가 전역에 살고 결과가
  다시 그 전역에 쓰이는 구조에서 LUT 결과가 자라면 인덱스가 테이블 뒤 메모리를
  읽는다. **호스트는 LUT 를 더 깊게 복사해서 그 초과 읽기까지 재현**해야 한다.

## 6. 박스 블러 — 한 프레임에 1.2초짜리

간유리 배경이 이 게임에서 가장 비싼 한 방인 경우가 많다. 출력 픽셀마다 k×k 상자를
다시 걷고, 그 다음 나눗셈을 세 번 부른다.

**규칙을 그대로 지키면서 분리 가능한 슬라이딩 윈도우로 바꾼다:**

* **화면 밖 표본은 클램프가 아니라 건너뛰기**인 경우가 많다. 그러면 **나눗수가
  픽셀마다 다르다**(= 잘린 상자의 표본 수). 이걸 상수로 바꾸면 가장자리가 틀린다.
* 절삭 나눗셈, 565 재조립 규칙(파랑 마스크, 초록은 시프트 뒤 마스크, 빨강은
  마스크 없음)을 그대로.
* 중간값이 전부 정확한 정수이므로 **결과는 픽셀 단위로 같고** 비용은
  O(w·h·k²) → O(w·h).
* 게스트가 결과를 **오프스크린 버퍼에 소스 폭으로** 채워 넣고(그 버퍼 자기 pitch 는
  무시) 다시 소스로 `memcpy` 하는 경우가 있다. **양쪽 다 재현**해야 한다 —
  스크래치가 관측 가능하고, 다음에 거기 그리는 것이 다른 바이트를 보게 된다.
* **소스와 스크래치가 겹치면 거절하라.** 호스트는 스냅샷으로 계산하므로 그때만
  결과가 달라진다.

## 7. GL 은 대개 구현할 필요가 없다

게스트가 스프라이트를 GL 로 그리지 않고 프레임버퍼에 직접 쓰는 구조라면,
GL 트래픽은 보통 이것뿐이다:

```
flushLcd -> glTexSubImage2D -> glDrawArrays(GL_TRIANGLE_STRIP, 4 정점)
```

즉 **축에 정렬된 사각형 하나**. 그러면 GL 구현이 아니라 **그 호출들을 지켜보다가
사각형 하나를 CPU 로 확대 복사하는 상태 기계**면 충분하다. 이득:

* 헤드리스 프로브와 실기기 앱이 **완전히 같은 렌더 경로**를 쓴다 → 결정적 A/B 가
  가능해진다.
* 비용은 프레임당 스케일 복사 한 번(실측 1~3 ms). 병목이 아니다.
* 레터박스 막대도 같은 텍스처에 색을 곱해 그리는 경우가 많다 — 그것까지 상태
  기계로 흉내 낸다.

## 8. 서피스 크기가 프레임버퍼와 다를 때

회전·분할화면·폴드 전환 중에는 서피스 크기가 프레임버퍼와 어긋난다. 그대로
`memcpy` 하면 **화면이 대각선으로 밀린다**(스트라이드가 안 맞아서). present 경로는
크기가 다르면 **스트라이드를 지키는 최근접 스케일로 폴백**해야 한다.
