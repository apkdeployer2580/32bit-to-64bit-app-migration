# 게스트 동작을 의도적으로 바꾸기

성능 이식(`frame-optimization`)은 **화면이 픽셀 단위로 같아야 한다**. 이 스킬은
반대다 — **일부러 다르게 만든다.** 그래서 규칙도 다르다.

## 0. 두 종류를 절대 섞지 마라

| | 성능 이식 | 동작 변경 |
|---|---|---|
| 목표 | 비트 단위 동일 | 의도적으로 다름 |
| 스위치 | `NO_PATCH` (기본 켜짐) | **기능별 개별 스위치** |
| 검증 | A/B 픽셀 동일 | A/B 로 **의도한 곳만** 달라짐 |
| 설치 조건 | 심볼만 있으면 | 심볼 + **명령어 워드 확인** |

성능 패치를 끄는 스위치와 동작 패치를 끄는 스위치는 **다른 스위치여야 한다.**
안 그러면 최종 A/B 에서 "SKIP 버튼 하나가 늘었다"가 회귀로 보인다.

## 1. 세 가지 후크 지점, 셋 중 하나를 고른다

### (a) 함수 진입점

가장 안전하다. 심볼 이름으로 걸고, 원하는 답을 `r0` 에 넣고 `PC = LR`.

**주의**: 그 함수에 호출자가 여럿이면 전부에 영향이 간다. 호출자가 하나라는
사실을 확인했다면 그렇게 적어 두어라.

### (b) 호출자로 거르는 진입점 후크 — `LR` 검사

같은 함수를 여러 곳에서 부르는데 **한 호출 지점만** 바꾸고 싶을 때:

```rust
let lr = self.cpu.reg_get(Mode::User, reg::LR);
if lr != base_of(caller) + KNOWN_OFFSET { return Ok(false); }   // 다른 호출자는 통과
```

`LR` 은 그 호출 지점의 다음 명령 주소다. 호출자 심볼 + 오프셋으로 표현하면
주소 하드코딩이 아니게 된다.

이 검사는 **재귀 방지도 겸한다** — 호스트가 `Vm::call` 로 그 함수를 다시 부를 때
`LR = RETURN_MAGIC` 이라 후크가 스스로를 다시 잡지 않는다.

### (c) 함수 중간의 특정 명령

가장 강력하고 가장 위험하다. 어떤 동작은 **함수 중간의 한 곳으로만** 수렴한다.
예: 하드웨어 키, 숫자 키 별칭, 그리고 **화면의 화살표 탭**이 전부 같은 스택
슬롯 하나로 모이는 지점.

이때 진입점에서 키 코드를 바꾸는 식은 **기기에서 아무 일도 안 한다** — 터치는
키 코드를 만들지 않고 히트 테스트 결과를 그 슬롯에 넣기 때문이다.

**중간 후크는 반드시 명령어 워드를 확인하고 설치한다:**

```rust
const SITE:  u32 = 0x32ec;          // 함수 진입 기준 오프셋
const WORD:  u32 = 0xe59d_201c;     // ldr r2, [sp, #0x1c]
if mem.r32(base + SITE) != WORD {
    log::warn!("...: guest code does not match; not installed");
    return None;
}
```

이유: `[sp+0x1c]` 같은 생 프레임 슬롯은 그 함수의 **다른 26곳에서 범용
스크래치**로 쓰이고, 다르게 빌드된 게스트에서는 완전히 다른 것을 가리킨다.
조용히 틀리느니 설치가 안 되는 편이 낫다.

### 분기만 돌려라 — 본체는 게스트 코드로

"이 조건에서도 이 기능이 동작하게" 하는 변경은 대개 **분기 하나를 돌리는 것**으로
끝난다. 히트 테스트, 진동, 실제 동작은 전부 게스트 코드에 이미 있다. 그것을
호스트로 다시 쓰면 그때부터 원본과 다른 게임이 된다.

## 2. 어떤 조건을 여는지 정확히 골라라

"이 UI 가 어떤 상황에서 사라진다"는 대개 **장면 단위가 아니라 코드/상태 단위**로
꺼져 있다. 실제 사례: 컷신 SKIP 버튼의 표시 여부가 이벤트 스크립트 **opcode 별
표**로 결정되고, 0인 항목이 아홉 개였다.

전부 여는 것은 거의 항상 틀린 답이다. 아홉 개 중:

* **두 개**만 열면 증상이 해결됐다(전체화면 나레이션, 화면 페이드).
* **여섯 개**는 자기 핸들러에서 진행 중인 동작을 **일부러 취소**하는 대화형
  화면이었다. 열면 UI 가 서로 싸운다.
* **한 개**는 함정이었다 — 그 상태가 입력을 잠그는 바이트를 매 틱 다시 세우고,
  그것을 푸는 모든 경로가 도달 불가라, 열면 다음 팝업을 영원히 못 닫는다.

**작업 방법**: 그 표/조건을 쓰는 곳을 전수 조사하고, 항목마다 "열면 무슨 코드가
도는가"를 한 줄씩 적은 뒤 고른다. 그 목록을 문서에 남겨라 — 다음 사람이 "왜
나머지는 안 열었지"를 다시 묻지 않게.

### 그리기만 열면 죽은 버튼이 된다

표시 조건과 **입력 조건이 따로** 있는 경우가 대부분이다. 그리기를 뚫었으면
입력 경로에서 같은 조건으로 거르는 지점도 같이 뚫어야 한다. 그 지점들은 보통
이미 "이미 진행 중인가" 같은 가드 뒤에 있어서, 거기에 붙이면 그 가드를 공짜로
물려받는다.

## 3. 원작 버그를 고칠 때 — 무엇을 되돌릴지가 핵심

전형적인 원작 버그: 어떤 중단 경로가 정규 teardown 을 **손으로 베껴 놓고
저장 몇 개를 빠뜨리고 하나를 더 지운다**.

* **빠뜨린 것**을 채우는 것은 대개 안전하다(관측 불가능한 것도 있다 — 그렇다면
  정직하게 "위생 조치"라고 적어라).
* **더 지우는 것**이 진짜 원인인 경우가 많다. 그런데 무조건 되돌리면 안 된다:
  그 필드를 **아직 필요로 하는 상태가 있을 때만** 되돌려라. 아무도 안 쓰는데
  살려 두면 이번엔 반대 방향의 버그(착탄하지 않은 것으로 판정이 도는 등)가 생긴다.

```
if (설치됨 || 복원대기) { 값을 되돌린다 }
else { 게스트가 지운 대로 둔다 }
```

**고치지 않을 것도 정하라.** 예: 쿨타임이 키를 누른 시점에 시작해서 중단된
동작도 쿨타임을 태운다면, 그것이 원본 동작이라면 그대로 둔다. 어디까지가
버그 수정이고 어디부터가 게임 개조인지 선을 긋고 문서에 적어라.

### 영구 래치는 별개 문제다

"한 번 이렇게 되면 프로세스가 끝날 때까지 안 돌아온다"는 부류는 대개 초기화
프레임에 중단이 들어와서 `total=0, elapsed=0` 같은 상태가 되고, 해제 조건
`total < elapsed` 가 영원히 거짓이 되는 식이다.

호스트는 진입에서 **그 삼중조를 보면 플래그만 지운다.** 게스트가 이미 처리하는
경우와 겹치지 않으므로 순수한 초집합이고, 그래서 안전하다. 이런 것은 조건을
정확히 적어 두어야 나중에 "왜 여기 특수 케이스가 있지"가 안 나온다.

## 4. 세이브에 박혀서 게임 안에서 못 바꾸는 값

세이브에서 읽은 값을 바꿀 setter 가 **바이너리 어디에서도 호출되지 않는** 경우가
있다(심볼 테이블에만 주소가 있고 `.text` 에는 없다). 그러면 한 번 그 값이 된
세이브는 영원히 그 상태다.

해결: **로드 함수를 감싸서 그 뒤에 값을 덮어쓴다.** 저장 함수가 그 필드를 도로
파일에 쓴다면 다음 저장 때 파일까지 고쳐진다.

```
touch pad mode: save says 1, forcing 0
```

이렇게 부팅 로그에 찍어라. 사용자가 "왜 바뀌었지"를 물을 때 답이 로그에 있다.

## 5. 그리기와 히트 테스트는 따로 논다

UI 요소를 옮기거나 키울 때 **그림만 옮기면 보이는 곳과 눌리는 곳이 어긋난다.**

* 히트 사각형은 보통 **키 핸들러 수십 곳에 복붙**돼 있고 공용 심볼이 없다.
* 사각형 값만으로 찾으면 한 곳을 빠뜨려 "이 화면만 안 눌리는" 버그가 생긴다.
* **값 AND 호출자 범위** 둘 다로 거르는 것이 맞다. 그래야 우연히 같은 값을 쓰는
  다른 사각형을 움직이지 않는다.
* 그림 쪽 좌표 변환과 **똑같은 변환**을 히트 사각형에도 통과시켜라. 1:1 에서 두
  박스의 중심이 같으면 그 관계가 유지된다.

### 크기를 키울 때는 다른 것을 안 먹는지 확인하라

히트 박스가 커지면 그 화면의 **먼저 검사되는** 사각형이 뒤의 버튼을 가릴 수 있다.
관련 핸들러의 히트 검사를 전부 뽑아 교차시켜서, 아무것도 안 뺏는 최대 배율을
찾아 기본값으로 삼아라. 그 한계를 문서에 적어 두면 나중에 키우고 싶은 사람이
무엇을 대가로 내는지 안다.

## 6. 죽은 플랫폼 서비스에 답하기

원본이 플랫폼(통신사 결제, 진동, 계정 서비스)에 물어보고 **콜백을 기다리는**
구조라면, HLE 가 `-1` 을 돌려주고 콜백을 부르지 않는 것이 **"무한 로딩"의 정체**다.
게스트는 플래그를 세운 채로 그 상태를 벗어나지 못한다.

호스트가 플랫폼 역할을 해야 한다:

1. 게스트가 등록한 콜백 포인터를 찾는다(`SetCB` 류 임포트에서 받아 둔다).
2. 진행 플래그를 지운다.
3. **콜백을 게스트 규약대로 부른다.** 규약은 디스어셈으로 확정하라 — 어떤
   레지스터가 성공/실패이고, 어떤 것이 쓰이기 전에 덮어써지는지.

지급·저장·연결 종료 같은 것은 전부 게스트 코드가 한다. 호스트가 할 일은
**답하는 것**뿐이다.

부작용을 미리 세어라: 같은 콜백을 쓰는 지점이 넷이면 넷 다 바뀐다. 서비스가
없어진 이상 선택지는 대개 "전부 통과" 아니면 "전부 영영 고장"뿐이고, 그렇다면
그것을 의도로 문서에 적어라.

## 7. 검증

동작 변경은 픽셀 동일이 기준이 아니다. 대신:

* **의도한 프레임만 다른가.** 예: 컷신 1300프레임 재생에서 950~1275 프레임이
  **바이트 단위 동일**이고 SKIP 버튼이 뜨는 구간만 다르다.
* **다른 진입 경로와 결과가 같은가.** 예: → 로 들어간 프레임이 OK 로 들어간
  프레임과 **바이트 단위 동일**, 그리고 스위치를 끄면 다름.
* **로그로 판정할 수 있는가.** 눈으로 "고쳐진 것 같다"가 아니라, 그 사건이
  일어날 때 한 줄이 찍히게 하라:
  `cast abort: skill N chain idx M held=H pending=P, chain index kept`

## 8. 스위치 규약

기능마다 개별 환경변수, **기본값을 문서에 적고**, 그리고:

> **환경변수와 빌드 시점 둘 다 읽어라.** 기기에는 환경변수를 설정할 방법이 없다.
> 빌드에 굽는 값을 바꿀 때는 해당 크레이트를 `clean` 해야 한다는 것도 같이 적어라
> (`option_env!` 는 환경 변경으로 재빌드되지 않는다).
